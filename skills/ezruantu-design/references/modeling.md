# 图种选择与建模规则

只读取当前任务涉及的图种。以下规则帮助把项目事实转成模型；字段结构、枚举和数量限制从当前 MCP Schema 获取。

## 选图依据

| 图种 / type | 需要回答的问题 | 主要依据 |
| --- | --- | --- |
| 概念 ER / `er` | 业务中有哪些实体，它们如何关联 | 需求、领域实体、业务数据规则 |
| 表关系 / `table` | 数据实际怎样存储、字段和关联是什么 | 实际模型、迁移、建表语句 |
| 用例 / `usecase` | 哪些角色能完成哪些业务目标 | 权限、需求、操作入口和业务服务 |
| 流程 / `flowchart` | 一个业务如何推进，条件和异常如何处理 | 具体流程的服务逻辑和业务规则 |
| 时序 / `sequence` | 一次交互由哪些参与者依次协作 | 请求链、服务调用、持久化与返回 |
| 类 / `class` | 类型的职责、成员和依赖是什么 | 实际类、接口、组合和继承定义 |
| 架构 / `architecture` | 系统由哪些部分组成，如何连接 | 部署配置、应用边界、模块依赖 |
| 功能结构 / `structure` | 系统功能怎样逐层分解 | 需求、菜单与模块职责 |

简单项目不一定需要类图或单独的部署架构图。全套设计按需覆盖数据、需求、总体结构和关键业务；用户明确指定的图种优先，不用上述清单扩张任务。

## 概念 ER 与表关系

- 概念 ER 描述业务实体、属性和联系；表关系图描述实际字段与存储结构。不要把技术表的全部字段机械展开为概念 ER 属性。
- 数据库没有声明外键，不代表没有业务关联。根据代码使用和业务语义表达逻辑关系，不声称数据库已经施加外键约束。
- `1`、`N`、`M` 可用于传统 ER；需要表达可选性时使用当前 Schema 接受的 `0..1`、`0..N`、`1..N` 等。此工具的产品偏好是不用重复的 `*` 标记，不把这个偏好解释成 UML 的通用禁令。
- 一对多和多对多从数据规则判断；实际中间表在表关系图中保留，概念图可直接表达业务联系。
- 字段类型取自实际模型或明确的目标设计。字符串长度、金额精度、时间类型不统一猜成 `varchar(100)`；未知类型可以留空并说明。

## 用例图

- 参与者表示角色或系统外部协作方；内部页面、服务和数据库通常属于时序图或架构图，不把它们当作普通业务角色。
- 用例名称描述用户目标，如“提交预约”“审核申请”；数据库表名、内部方法名不是直接可用的业务用例。
- `association` 连接参与者与用例；`include` 从基础用例指向被包含用例，`extend` 从扩展用例指向基础用例。只有业务上确有必经复用或条件扩展时才使用这些关系，不为凑关系把所有用例串起来。
- 此应用要求用例图优先直线或斜线，避免直角折线；由自动排版处理参与者位置、分组和避让，不通过更改业务关系或手填坐标掩盖排版问题。
- 不为图中孤立节点虚构业务关联。源码能证明关系时再补；否则保留现状并指出待确认的含义。

## 流程图

- 表达一个有边界的业务过程。处理节点写动作，判断节点写条件，分支文字与条件一致。
- 正常流程沿主轴推进，异常或替代分支放侧边；每条分支有明确去向。成功、失败可以进入同一结束，也可以有不同结果，取决于真实业务。
- 开始/结束的胶囊形和椭圆都可表达终止符，保持同图一致；不因外观差异改写业务含义。
- 不增加无业务含义的实心合流圆点。对连接线、箭头与标签的问题，先核对排版结果而不是修改步骤内容。

## 时序图

- 按一次具体场景写参与者和消息顺序，区分调用方、界面/接口、业务服务、持久化或外部系统。
- 返回消息与实际调用对应；同步调用和返回分别使用当前模型支持的关系类型，激活条由渲染器计算。
- 业务校验通常发生在业务服务；数据库消息按实际操作写查询、写入或事务。若项目确实使用数据库约束或存储过程校验，应忠实体现。
- 不把所有业务塞进一张时序图；复杂成功/失败场景可拆图。当前工具不支持的 `alt`、`loop` 等复杂片段，不伪造为已经实现的图形能力。

## 类图

- 来自实际类、接口和职责，保留有意义的属性、方法和依赖，不把所有文件或每个数据库表强行变成类。
- 继承从子类指向父类；依赖从使用方指向被使用方。关系类型和成员表达方式以当前 Schema、模板为准。
- 项目没有对应类结构时，说明类图的适用范围；用户要求目标设计时可以设计类职责，但要区分现状与建议。

## 架构图与功能结构图

- 架构图表现组件和交互，数据库、消息队列、缓存和外部服务采用项目实际技术；不把常见技术栈默认当作已经存在。
- 功能结构图表现功能分解，层级粒度一致，父节点涵盖子节点。调用依赖适合架构图，不用层级循环表示共享功能。
- 同一张图避免混合“部署机器、数据库字段、用户操作、代码函数”四种粒度。多层细节可拆成总体图和局部图，而不是删掉实际信息。

## 跨图一致性与版面

同一实体、角色和业务动作应能跨图对应。表名可使用代码标识，业务图可用中文名称，但含义保持一致。遵守用户或学校给出的符号、命名和格式要求。

自动排版后抽查相关节点是否归组、标签是否遮挡、箭头尖端是否正确连接轮廓、文字是否裁切。复杂项目按语义拆图；保留模型数据，并清楚说明渲染限制，不能把“用户再拖一下”当成自动排版完成。
